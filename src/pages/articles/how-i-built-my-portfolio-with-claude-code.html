How I built my portfolio with Claude Code

And what rebuilding it from scratch taught me about AI native workflows, better briefs, and the difference between generating output and directing work.

I am a product designer. I am not a developer. I know enough HTML and CSS to be dangerous, I once watched a YouTube tutorial about React before closing the tab after eleven minutes, and my previous portfolio lived comfortably on Webflow where nobody had to know any of that.

So when I decided to rebuild from scratch using Claude Code, VS Code and Vite, I was either being ambitious or foolish. Probably both.

This is the honest story of how it went.

Why not just use Webflow?

My old portfolio worked fine. It looked decent. But I kept hitting the ceiling of what I could do without touching code, and every time I wanted something slightly different I was fighting the platform rather than building the thing.

More importantly, I kept hearing product teams talk about AI native workflows. Designers who could move between Figma and code fluently. Designers who understood what they were handing to engineers. I wanted to be one of those designers, and the only way to get there was to actually do it.

How it actually worked

I want to be honest about this because I think a lot of people have the wrong idea about what building with AI actually looks like.

Claude Code did the heavy lifting on the architecture. It chose the folder structure, set up the CSS system, built the component library and made the technical decisions I would not have known to make. I did not architect this codebase. Claude Code did.

What I did was manage the outputs. I wrote the briefs. I made the design decisions. I defined the colour palette, the fonts, the spacing system, the reference sites. I reviewed everything Claude Code built, caught the things that were wrong, and refined until it was right. I wrote the copy. I placed the images. I decided what the site should feel like and communicated that clearly enough for Claude Code to execute it.

The best analogy I can think of is briefing a contractor. A good contractor will build something solid if you give them a clear brief. A vague brief produces something you spend ages fixing. The quality of what Claude Code builds is almost entirely determined by the quality of what you ask it to build.

The thing that made the biggest difference

Early on I created a CLAUDE.md file, a plain text document that lived in the project root and told Claude Code everything it needed to know before starting any task.

My colour tokens, my font choices, my spacing system, my reference sites, how I like to work. Every session started with Claude Code reading that file. The outputs were significantly better for it.

It is essentially a design brief that lives inside the codebase. I would recommend it to anyone doing the same thing.

The honest bits

It did not always go smoothly. Claude Code occasionally ignored the brief and invented its own decisions. There were em dashes everywhere for a while. At one point it introduced something called Handlebars templating that nobody asked for. There were several incidents involving a burger menu and an X button that refused to align.

But every time something went wrong I learned something. And I got better at writing briefs. The prompts I wrote at the end of the project were significantly better than the ones I wrote at the start. Specific, scoped to one thing, referencing exact decisions I had already made. Those got clean outputs first time.

What I ended up with

A live portfolio at samsux.co.uk. Three case studies with real images and real outcomes. A mobile navigation I am genuinely proud of. An About page with a story about a Wetherspoons breakfast that people seem to remember.

And a story to tell in interviews that goes well beyond "I can use Figma."

What I would tell anyone thinking about doing the same

You do not need to be a developer. You need to be a good communicator, which if you are a designer you already are.

Write the brief before you build anything. Define what you want before Claude Code touches a file.

Manage the outputs. Review everything. Catch the things that are wrong. Refine until it is right. That is the job.

And push to GitHub constantly. Every time you are happy with something. Future you will be grateful.
